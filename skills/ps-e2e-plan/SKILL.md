# E2E Test Planning — Router Discovery, API Scenarios, Frontend Routes

This skill **plans scenarios; it does not create or execute tests**. All arguments are natural-language skill arguments processed from the user request, not OS-shell switches. Accept `-role backend` as an informal alias for `--role backend`; the documented form is `--role`.

## Argument defaults and intended commands
- `/ps-e2e-plan --role backend` → **repository-wide** backend router discovery, full endpoint inventory and API scenarios, without requiring a Wave or GitHub issue.
- `/ps-e2e-plan --role backend --scope all-routes` → same explicit full inventory.
- `/ps-e2e-plan W1 --role backend --target api --scope all-routes` → enumerate **all** repository endpoints, label those connected to W1 as `IN WAVE` and other endpoints as `OUTSIDE WAVE` / `UNMAPPED`; do **not** claim the entire project is in W1.
- `/ps-e2e-plan W1 --role backend --target api` → default Wave-focused API plan, with a complete inventory only of route registration files relevant to the Wave; state that this is not full repository coverage.
- `/ps-e2e-plan --role backend --router-file src/routes/api.ts` → focus on the specified router file, follow mounts/imports to get effective paths, and mark the inventory `FILE-SCOPED` (not all routes).
- `/ps-e2e-plan --role backend --router-dir src/routes --scope all-routes` → explicitly search a router directory **plus** its mounting modules; still search for registrations outside the directory and report whether the scan could be complete.
- `/ps-e2e-plan W1 --target both` → prior behavior: plan API + frontend routes + browser-to-API journeys scoped to an approved Wave.
- Default `--target api` when `--role backend` and the user did not state a target. Otherwise default `--target both`. `--scope all-routes` is never inferred from a Wave ID unless explicitly supplied.
- Unknown flags, unresolved local repository, or inaccessible requested `--router-file` → report `BLOCKED` or ask for the missing authoritative input; never guess endpoints.

## Read-only repository discovery (backend/API)
1. Confirm the current working directory is the intended repository. Read applicable `CLAUDE.md`, READMEs and architecture files; check `git status` without altering it. The CLI `gh` and GitHub Issues are optional for **repository-wide** discovery. For a Wave/Issue plan, require an authoritative Wave/Issue definition to claim Issue coverage; if unavailable, still produce a repo inventory clearly marked `UNMAPPED` and state which traceability is blocked.
2. Determine stack/framework and search for **registration entry points**, not only files named `router`: `routes`, `routers`, `api`, `controllers`, `endpoints`, `handlers`, `openapi`, `swagger`, HTTP gateway modules and server/bootstrap files. Examples to examine as applicable: Express `app.use`/`Router`, Fastify `register`/prefixes, NestJS controller decorators and global prefix, Next.js API route handlers, Django `urlpatterns`/`include`, FastAPI `include_router`, Laravel route groups and `routes/api.php`, Rails routes, Spring `RequestMapping`, ASP.NET endpoint/controller mappings, Go mux/gateway registration. Do not assume the project uses any particular framework.
3. Follow imports, nested routers, mounts, group prefixes, API version prefixes, conditional middleware and inherited auth guards until the effective **HTTP method + normalized URL path template** is resolved. Identify environment-conditional routes and explicitly record uncertainty. Do not count the same route twice because it appears in multiple files. Exclude third-party dependencies, compiled artifacts and generated copies unless they are the authoritative routing source. Record runtime-discovered/generated routes as `UNVERIFIED` where static analysis cannot prove completeness.
4. Cross-check route inventory against existing OpenAPI/Swagger specs, controllers/service implementations, frontend API clients (as supporting evidence), and existing API tests. Distinguish `VERIFIED IN CODE`, `DOCUMENTED ONLY`, `INFERRED` (not verified), and `DYNAMIC / UNRESOLVED`. Document unreachable/orphaned handlers separately, not as registered endpoints. Do not invent missing schemas, status codes, business rules, auth roles or paths.
5. For **every verified method+path**, record: stable API ID, HTTP method, full effective path, source file + registration/mount/controller evidence, owning module, middleware/auth/roles (or `UNKNOWN`), parameters/query/headers/body (or `UNKNOWN`), success behavior (supported by code/spec), error behavior (supported by code/spec), existing tests, related Issue/AC/Milestone/Wave if known, and inventory confidence. If code conflicts with spec, report the difference, do not silently choose one.
6. Generate **proposed** scenario rows per endpoint, choosing relevant cases rather than automatically inventing behaviors: happy path; required field/shape/boundary validation; unauthenticated/unauthorized/object access where applicable; unknown resource; malformed path/query; response/status/contract assertions; duplicate/replay/idempotency for state-changing or payment endpoints if relevant; filtering/pagination/sort if exposed; error handling; cleanup and repeatability. When expected behavior cannot be established, record `EXPECTED: TBD (requires contract)` and `BLOCKED`, not a made-up HTTP status.
7. Each scenario needs: scenario ID, endpoint ID, method/path, positive/negative/security/contract classification, setup/fixtures, identity/authorization, request inputs, **evidence-backed** expected status/body/side effects, cleanup, severity/priority, proposed Playwright API test path (`tests/e2e/api/...` unless the repository specifies another convention), owner `backend` or `qa` as context dictates, and implementation state `EXISTING | PROPOSED | BLOCKED | NOT APPLICABLE`.
8. Never send actual HTTP requests, start services, install dependencies, write tests, populate databases, use production tokens or modify GitHub during planning. Do not put secrets in outputs. Ensure the proposed tests use non-production environments and isolated deterministic test data when executed later.
9. Summarize **discovery coverage**: registered routes verified, documented-only routes, dynamic/unresolved registrations, routes with planned scenarios, routes with existing tests, and routes lacking reliable contracts. Planned scenario coverage is **not** an executed test pass rate. List the directories and entry points searched plus important exclusions and limitations. Explain why full enumeration may be impossible in a dynamic application.

## Frontend and cross-layer behavior (when selected)
10. For `--target frontend` or `both`, discover UI route registration, pages/components, auth rules and API usage. Build a frontend route inventory with path, source, validation/empty/error/loading states, browser checks, issue/AC mapping and existing tests.
11. For `--target both`, create user-journey scenarios correlating frontend action → HTTP method + endpoint → observable backend state → UI feedback. Mark tests `PROPOSED` until written/executed; include integration dependencies and permission constraints.
12. Maintain Milestone/Wave/Issue mappings where evidence exists; for repository-wide scan without approved Wave, set mappings to `UNASSIGNED` instead of blocking the route inventory.

## Output and approval
Present concise summary, then tables (or a link to approved file output) with:
- **API Route Inventory:** `API ID | Method | Effective Path | Source | Auth | Evidence/Confidence | Wave/Issue | Existing Test`.
- **API Scenario Matrix:** `Scenario ID | API ID | Category | Setup/Input | Expected Result/Evidence | Priority | Proposed Test File | Status`.
- **Coverage & Gaps:** registered route count, confirmed/documented/dynamic counts, proposed-vs-existing scenario coverage, unknown contracts, unlinked Issues, and risks.
- If no endpoints are confidently discovered, report `BLOCKED` with what was searched; never output fake examples as real API inventory.
- Draft from `templates/API-ROUTE-INVENTORY.md`, `templates/API-E2E-TEST-PLAN.md` and `templates/E2E-PATH-COVERAGE-MATRIX.md`. For frontend use `templates/FRONTEND-E2E-TEST-PLAN.md` and `templates/E2E-TEST-PLAN.md`.
- Suggest locations under `docs/ps-flow/e2e/REPOSITORY/` or `docs/ps-flow/e2e/<WAVE-ID>/`, for example `API-ROUTE-INVENTORY.md`, `API-E2E-TEST-PLAN.md`, `E2E-PATH-COVERAGE-MATRIX.md`.
- **STOP for approval** before writing files to the app repository, generating actual test code, running tests, installing Playwright, starting services, provisioning data or any GitHub modification. To implement/run the approved plan later, use `/ps-e2e-test` with the approved scope and environment.
