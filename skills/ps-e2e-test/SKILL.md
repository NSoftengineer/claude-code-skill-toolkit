# Execute E2E tests by target (API / FRONTEND / both)

1. Require an explicit Wave/Issue, approved path/route coverage plan, exact authorized non-production URLs for each required surface, safe test users/credentials, and approval to execute the selected tests. `--target both` is the default. Never guess an endpoint or assume the server is running.
2. Check local project `CLAUDE.md`, `package.json`, lockfile, `playwright.config.*`, Playwright dependency and browsers, test sources, allowed environment and how API/frontend `baseURL` are configured. Playwright's `request` fixture / `APIRequestContext` supports API tests; browser/page fixtures support frontend; their base URLs and test projects may differ.
3. Identify exact approved test IDs/files/tags by scope. Select them using existing repository conventions (`--project` only if the named Playwright project exists, otherwise file path/tag filters). Do not assume `--project=api`, `--project=frontend`, or directories exist; never silently run an unrelated suite.
4. For `api`, exercise the approved HTTP methods/path templates against the configured `API_BASE_URL` (or the project's actual config); assert status, response shape/contract, negative cases and appropriate auth without dumping tokens. For `frontend`, visit the approved `FRONTEND_BASE_URL` routes with browser assertions. For `both`, include approved API tests, browser tests, and cross-layer tests that verify browser behavior is backed by expected API/state changes; separate execution groups only where the repository supports them.
5. Never create test data, run mutating API calls or start external services without the explicit environment and data-operation authorization. No production, real payments, live customer records or destructive operations. Use disposable staging fixtures and an approved cleanup strategy.
6. Do not install dependencies or browsers, create tests, overwrite Playwright config, or edit application code. If tests are PROPOSED but not implemented, report `BLOCKED` for execution and request separate approved test implementation.
7. Before the run, display the **exact** command(s), selected test files and project names, redacted URLs, test data side effects and unique output folder `reports/<wave>/runs/<UTC-run-id>/`; run only after authorization. Set applicable Playwright reporter paths via `PLAYWRIGHT_JSON_OUTPUT_FILE`, `PLAYWRIGHT_JUNIT_OUTPUT_FILE`, `PLAYWRIGHT_HTML_OUTPUT_DIR`, `PLAYWRIGHT_HTML_OPEN=never` and supported reporters (`line,json,junit,html`), without overriding custom project requirements. On Windows use PowerShell `$env:` syntax.
8. Keep raw artifacts clearly traceable by target: `api/`, `frontend/`, and `integration/` (where executed), or a single reporter output plus reliable per-test metadata. Never pretend a mixed suite is separated when source data cannot attribute tests.
9. Preserve exact commands, exit codes, UTC timestamp, Git commit, browser and environment used, reporter results, and evidence paths. `--target both` is PASS only if **each applicable required target** has actually executed and passed; a passing API-only run is never a frontend PASS.
10. Status PASS / FAIL / PARTIAL / BLOCKED / NOT RUN, with per-target results and next actions. STOP; do not mutate GitHub, start next Wave, push, or deploy.
